# BAAM PvE 모드 기획서

`Game-Design-Document.md` **§16 의 하위 문서**다. 상위 규칙(판정·턴·카드·장비)은 GDD 가 정본이고,
이 문서는 §16.5 가 미결정으로 남긴 항목을 구체화한다. **PvP 규칙은 이 문서로 바뀌지 않는다.**

> 섹션 번호를 GDD 와 겹치지 않게 `E` 로 시작한다 — 코드 주석이 GDD 번호(§4.2 · §13.1 등)를
> 직접 참조하고 있어, 두 문서가 같은 번호를 쓰면 어느 쪽을 가리키는지 알 수 없어진다.

## E1. 설계 전제

§16 이 못박은 전제는 하나다. **새 게임 로직을 만들지 않는다.**

이 전제는 장식이 아니라 예산이다. PvE 를 "다른 게임" 으로 만들면 카드 31종·판정·장비·연출을
두 벌 유지해야 하고, PvP 에 카드를 하나 추가할 때마다 PvE 쪽을 함께 고쳐야 한다.
그래서 이 문서의 모든 제안은 다음 질문을 통과해야 한다.

> **이것을 PvP 코드를 고치지 않고 만들 수 있는가?**

통과하지 못하는 항목은 다섯이다. 가장 위험한 두 곳 — `ABGPlayerController` 의 카드 사용
경로와 `CheckWinCondition` 의 승패 판정 — 은 건드리지 않는다.

| 구조 변경 | 어디 | 단계 |
|---|---|---|
| PvE 전용 역할·직업 배정 (`BuildRolePool` 우회 + 적 직업 화이트리스트) | `ABGGameMode` | E-1 |
| PvE 최소 인원 완화 | `UBGMatchStartComponent` | E-0 |
| 진영별 덱 + `FBGCardInstance.Side` + 진영별 초기 손패 | `ABGGameState` · `FBGCardInstance` | E-3 |
| 조우 반복용 걸쇠 리셋 경로 | `ABGGameState` · `UBGMatchStartComponent` | E-4 |
| `AbilityByCardId` 를 공유 자산으로 올리기 | `ABGGameMode` 또는 DataAsset (E2) | P2 리팩터 |

### 재활용되는 것

| 시스템 | 그대로 쓰는가 | 근거 |
|---|---|---|
| 4단계 확률 판정 | ✅ 손대지 않음 | 서버 권위라 행동 주체가 사람이든 AI 든 같다 |
| 카드 효과 (`OutcomeEffects`) | ✅ | 데이터라 모드를 모른다 |
| 장비 (파란 카드) | ✅ | 적 강화를 장비로 푸는 근거 (§16.2) |
| 좌석·턴 진행 | ✅ | `CanSeatPlayCards` 가 좌석 기준이다 |
| 카드 사용 경로 | ✅ | `HandlePlayCard` 가 `protected` — 봇이 상속으로 호출한다 (E2) |
| 손패 분배·상한 | ✅ | `DrawCardsToHand` 가 좌석을 모른다 — 적도 같은 경로로 채워진다 (E5) |
| 승패 판정 | ✅ | E3 의 역할 고정 배정으로 그대로 성립한다 |
| 연출 (카드·사망) | ✅ | `ABGGameState` 의 단계 축이 좌석을 모른다 |
| 밧줄 (제한 시간) | ⚠️ 조정 | AI 턴에는 붙일 이유가 없다 — 단 E-2 부터 (E6 참고) |

## E2. 지금 코드가 PvE 를 막는 지점

§16.4 는 "AI 미구현" 이라고만 적혀 있는데, 실제로 걸리는 것은 AI 알고리즘이 아니라
**좌석을 차지하는 주체**다.

```
UBGSeatComponent::AssignSeatOnJoin(APlayerController* NewPlayer)
                                   ^^^^^^^^^^^^^^^^^ 좌석은 PlayerController 에 묶여 있다

ABGPlayerController::HandlePlayCard(InstanceId, TargetSeat)
^^^^^^^^^^^^^^^^^^^ 카드 사용 규칙 전체(검증·판정·GA 발동·연출 시작)가 여기 있다
```

즉 **PlayerController 가 없으면 카드를 낼 수 없다.** 반대로 `ABGPlayerState` 는
손패·장비·좌석의 정본이고 `ABGGameState::CanSeatPlayCards(Seat)` 는 좌석 번호만 보므로,
그 둘은 AI 에게도 그대로 쓸 수 있다.

### 두 갈래

**(A) 봇 PlayerController 를 스폰한다** — 연결 없는 `ABGPlayerController` 를 서버가 직접 만든다.
좌석·손패·카드 사용 경로를 **한 줄도 고치지 않는다.**

**(B) `HandlePlayCard` 를 GameState/GameMode 로 옮긴다** — 구조상으로는 이쪽이 옳다.
카드 사용은 규칙이지 입력이 아니다. 하지만 PvP 의 검증된 경로를 통째로 건드린다.

### 권고: (A) 를 먼저

E1 의 전제를 코드 수준에서도 지키는 쪽이다. (B) 는 PvP 가 안정된 뒤 P2 이후 리팩터로 남긴다 —
그때 옮기더라도 봇은 얇은 호출자만 바꾸면 되므로 (A) 가 (B) 를 막지 않는다.

### 상속으로 얻는 것

`ABGPlayerController` 는 수정하지 않는다.

| 필요한 것 | 접근 |
|---|---|
| 카드 사용 | `HandlePlayCard` — `protected` (`BGPlayerController.h:324`) |
| 턴 종료 | `RequestEndTurn()` — `public` (`:125`) |
| 턴 감지 | `OnTurnStateChanged` — `public`. `SetPhaseTag`/`SetCurrentSeat` 가 `HasAuthority()` 아래서 직접 브로드캐스트하므로 서버에서도 발화한다 |
| 로비 인원 집계 | `UBGReadyComponent` 가 `ABGPlayerState` 생성자에서 자동 생성된다. 봇은 `SetReadyAuthoritative(true)` 만 부른다 |
| 좌석·역할·직업 배정 | `CollectPlayers()` = `GetPlayerControllerIterator()`, `CountLobby()` = `PlayerArray` — 봇이 자동으로 포함된다 |

`AIModule` 은 필요 없다. `AAIController` 는 PlayerState 도 `PlayerArray` 도 없어 위 배정 경로를
전부 놓친다.

### ⚠️ (A) 의 함정 — 봇 BP 를 `BP_BGPlayerController` 의 자식으로 만들지 않는다

HUD 위젯을 만드는 것은 C++ 이 아니라 **`BP_BGPlayerController` 의 그래프**다. 그 BP 가
`WBP_BGHUD` 를 만들어 `SetHandWidget`/`SetSeatBoardWidget` 을 호출한다. 자식으로 만들면
화면 없는 봇이 HUD 를 만들고, 봇 수만큼 겹쳐 뜬다.

**봇 BP 는 `ABGAIPlayerController`(C++) 직속으로 만든다.**

C++ 쪽 UI 함수들은 위젯이 `nullptr` 이면 스스로 빠져나오므로 봇에서 돌아도 무해하다
(`IsLocalController()` 가드가 있는 곳은 `PlayResolveShake` · `EnsureCinematicCamera` ·
`HandleCameraShotChanged` 셋이다). 위젯을 **만드는** 쪽만 막으면 된다.

### `AbilityByCardId` — (가) 로 시작하고 나중에 (나) 로 리팩터

`HandlePlayCard` 는 `AbilityByCardId`(카드 → GA 매핑)에서 GA 를 찾고 없으면 카드를 거부한다.
이 맵은 C++ 기본값이 없고 BP 디폴트에서만 채워진다. 위 함정 때문에 봇 BP 를 분리하면
매핑이 두 곳에 생기고, 카드를 추가할 때 한쪽만 채우면 봇만 그 카드를 못 쓴다.

| 안 | 대가 |
|---|---|
| (가) 봇 BP 에 맵 복사 | PvP 0줄 수정. 중복 유지 부담 |
| (나) GameMode 나 DataAsset 으로 올려 공유 | 작은 PvP 수정. 중복 소멸 |

**(가) 로 시작한다.** E1 의 전제를 지키고 봇을 먼저 굴려 보는 것이 우선이다.
**(나) 는 E2 의 (B) 와 함께 P2 리팩터로 묶는다** — 둘 다 "카드 사용 규칙을 PC 밖으로 꺼내는"
같은 방향이라 따로 하면 같은 코드를 두 번 건드린다.

그동안 카드를 추가하면 **봇 BP 의 맵도 함께 채워야 한다.** 빠뜨리면 봇만 그 카드를 못 쓰고
조용히 넘어가므로, 카드 추가 체크리스트에 이 항목을 넣을 것.

## E3. 역할 — 제거하지 않고 고정 배정한다

§16.5 의 첫 미결정. "역할 시스템을 PvE 에서 어떻게 다룰지 (제거 / 단순화 / 유지)".

### 결론: 유지하되 배정을 고정한다

| 좌석 | 역할 | 서사 |
|---|---|---|
| 플레이어 | `Role.Sheriff` | 용사 |
| AI 전부 | `Role.Outlaw` | 마왕군 |

**`CheckWinCondition` 을 한 줄도 고치지 않아도 그대로 맞는다.**

```
보안관 사망            → 무법자 승  =  플레이어 패배  ✅
무법자·배신자 전멸      → 보안관 승  =  플레이어 승리  ✅
```

역할을 제거하는 쪽이 직관적으로 보이지만, 그러면 승패 판정을 PvE 전용으로 새로 써야 한다 —
E1 의 전제를 첫 항목부터 어긴다. 배정만 바꾸면 규칙 코드가 통째로 재활용된다.

### PvE 전용 배정 경로가 필요하다

승패 판정은 재활용하지만 배정 경로는 그렇지 않다.

```
BuildRolePool(4) → { Sheriff, Renegade, Outlaw, Outlaw }   // 보안관·배신자가 항상 들어간다
```

기존 풀을 쓰면 4인 PvE 에서 적 3명 중 1명이 배신자가 되어 위 표의 "AI 전부 `Role.Outlaw`" 가
나오지 않는다. 그리고 `AssignRoles`/`AssignJobs` 는 각자 `Num < MinPlayers(4)` 가드를 갖고 있어
3인 판에서는 **배정이 조용히 취소된다** — 경고 로그만 남고, 직업이 유일한 스탯 출처이므로
체력 0 인 캐릭터가 앉는다.

**PvE 전용 배정 경로를 만든다.** 사람과 봇은 `Cast<ABGAIPlayerController>` 로 가른다.
그 경로가 자기 규칙을 가지면 위 가드를 전부 우회하고, E7 의 최소 인원 완화와
적 직업 화이트리스트도 같은 자리에서 처리된다.

### 부관과 배신자

- **부관은 쓰지 않는다.** 아군 AI 를 넣으면 "보안관이 부관을 쏘면 전 재산 몰수" 라는
  원작 벌칙이 살아나는데, PvE 에서 그 규칙은 학습 대상이 아니라 사고다.
- **배신자는 후반 레벨의 변주로 남긴다.** 적 하나를 `Role.Renegade` 로 두면 마지막 1인이
  됐을 때 승리 조건이 갈린다 — 코드 변경 없이 난이도 축이 하나 늘어난다.
  다만 E7 의 레벨 표에서 **선택 항목**으로 둔다(먼저 검증할 것이 아니다).

  ⚠️ 이 축을 살리려면 **배신자 적에게 다른 행동을 줘야 한다.** AI 는 승리 조건을 추론하지
  않으므로(§16.3), 역할만 바꾼 배신자는 플레이어 입장에서 무법자와 똑같이 움직인다 —
  어느 쪽이든 전멸시켜야 이기고 죽으면 진다. 성격·직업·장비를 함께 다르게 배정해
  "저 하나는 다르게 싸운다" 가 화면에서 읽히게 할 것.

### 은닉은 하지 않는다

역할 은닉은 사람이 상대일 때만 재미가 된다(§16.2 가 이미 인정). PvE 에서는
적의 역할을 처음부터 공개한다 — `ABGPlayerState::SetPublicRole` 을 판 시작에 부르면 된다.

### ⚠️ E-1 확인 항목

무법자 승(= 플레이어 패배)에서도 `SetMatchEndStage(EBGMatchEndStage::Victory)` 가 불린다.
이름이 `Victory` 지만 실제로는 "종료 연출" 단계다. UI 가 이것을 "승리" 로 표시하는지는
BP 쪽이라 E-1 에서 눈으로 확인한다. PvP 에서도 같은 경로를 타므로 이미 처리돼 있을 수 있다.

## E4. 한 판의 구조

```
런 시작 → 직업 배정 → [조우 1] → 보상 → [조우 2] → 보상 → … → [보스 조우] → 런 종료
                        └ 기존 BAAM 한 판 그대로 (판정·턴·연출 전부 동일)
```

- **조우(Encounter) = 기존 BAAM 한 판.** 레벨이라는 말 대신 조우를 쓴다 —
  "레벨" 은 UE 의 맵과 헷갈린다.
- **직업은 고르지 않는다 — 지금처럼 랜덤 배정한다.** 슬더스가 캐릭터를 고르게 하는 것은
  캐릭터마다 전용 카드 풀이 있기 때문인데, BAAM 의 12종은 **전부 같은 덱을 쓰고 패시브
  하나만 다르다.** 그 차이로는 런의 첫 결정이 성립하지 않고, 고르게 하면 플레이어가 최강
  하나(사냥꾼·용병)만 골라 나머지 10종이 안 쓰인다. 랜덤이면 런마다 다른 직업이 강제되어
  12종을 다 겪는다. PvP·원작과도 같은 규칙이라 E1 전제에 맞고 UI 작업도 없다.
  런을 여러 번 돌려 "매번 같은 느낌" 이 실측되면 그때 **랜덤 3종 중 1택**으로 붙인다 —
  보상 화면과 같은 위젯 패턴이라 재사용할 수 있다.
- 조우가 끝나면 맵을 갈아엎지 않는다. 같은 모닥불 자리에서 적만 새로 세운다.
  아트 기획서의 "모닥불 중심 원형 배치" 가 그대로 유지되고, 레벨 로딩이 없어 회전이 빠르다.

### 조우 사이에 이어지는 것 / 리셋되는 것

| | 이어짐 | 근거 |
|---|:--:|---|
| 플레이어 덱 (획득 카드) | ⬜ 미정 | 메인 기획 결정 대기 |
| 플레이어 장비 | ⬜ 미정 | 메인 기획 결정 대기 |
| 플레이어 체력 | ❌ 리셋 | 조우마다 새로 시작한다 |
| 손패 | ❌ 리셋 | 조우마다 새로 뽑는다 |
| 적 전부 | ❌ | 조우마다 새로 세운다 |

체력은 조우마다 리셋하는 것으로 확정됐다. **덱·장비는 아직 미정** — 메인 기획이 다시 정해야 한다.
현재 코드(조우마다 `ServerTravel` 로 GameState/PlayerState/ASC 를 새로 만들고 `InitializeDeck` 이 매번 덱을 새로 구성하는 것)는 사실상 덱·장비도 리셋되는 동작이지만, 이것이 **의도된 설계인지는 아직 확인되지 않았다** — 덱·장비 지속이 필요하다고 결론 나면 수정이 필요하다.

### 조우 리셋 경로

"적만 새로 세운다" 를 하려면 한 번만 켜지는 걸쇠 셋을 되돌려야 하는데, 되돌리는 코드가 없다.

| 걸쇠 | 위치 | 되돌리는 코드 |
|---|---|---|
| `bMatchStarted` | `UBGMatchStartComponent` (private) | 없음 |
| `bInitialized` | `ABGGameState` | 없음 ("게임 초기화시에만 false 로 되돌릴 것") |
| `bMatchRunning` | `ABGGameState` | `GameOver` 에서만 false |

**E-4 에서 `BeginNextEncounter()` 류의 리셋 경로를 만든다.**

## E5. 덱

§16.5 의 미결정 "PvE 덱의 구체적인 장수와 구성".

### 카드 풀

PvP 와 PvE 가 같은 풀을 쓴다. 카드 수는 층위가 넷이고, 섞으면 보상 풀(E8)과 적 덱 구성을
잘못 계산한다.

| 층위 | 수 | 출처 |
|---|--:|---|
| 선언된 `Card.Id.*` 태그 — 설계상의 카드 세계 | **31종** | `BGGameplayTags.cpp` |
| GDD §13.1 이 "Row 로 두되 `QuantityOfCard = 0`" 으로 계획 | 8종 | 빗나감·인디언·개틀링 + 무기 5종 |
| 현재 DT Row (전부 활성) | **12종 / 74장** | `DT_BGCard` uasset |

⚠️ `Card-Data-Spec.md` 와 `Code-Audit-And-Migration-Plan.md` 는 검증 기대값을
`11 종류 / 64 장`, `BG.ExpectedDeckSize 64` 로 적어 뒀는데 **낡았다.** 뱅이 12→20,
속공이 8→10 으로 늘고 요정 갑옷이 2장 들어가 지금은 **12 종류 / 74 장**이다.
그 두 문서의 기대값을 갱신해야 한다.

**E1 의 예산 논거는 31종 기준이고, PvE 실무 수치는 12종 기준이다.** GDD §6.2 가 "삭제가 아니라
경로 차단이다" 라고 못박았고 술통·감옥도 §6.3 의 자동 판정형 장비로 살아 있다.

⚠️ GDD §13.1 이 Row 로 두라고 지시한 8종이 `DT_BGCard.json` 에 없다. GDD §11 은
"`BG_DumpDeck` 이 `QuantityOfCard = 0` 인 종류를 알려준다" 를 비활성 확인 수단으로 정해 뒀는데,
Row 가 없으면 그 진단이 요정 갑옷 하나만 잡는다. E11 의 정합 과제에 포함한다.

### 현재 12종

정본은 `Docs/Card-Data-Spec.md` 이고 **데이터 정본은 uasset** 이다(E11 참고 — JSON export 는
최신이 아니다). 아래는 PvE 관점의 요약이다.

| 카드 | 타입 | 대상 | 공격 | 매수 | 성공/대성공 | Success 효과 |
|---|---|:--:|:--:|--:|--:|---|
| 뱅 | 갈색 | ✅ | ✅ | **20** | 65 / 10 | `DamageTarget 1` |
| 속공 | 갈색 | ✅ | ✅ | **10** | 65 / 10 | `DrawSelf 1` + `DamageTarget 1` |
| 맥주 | 갈색 | — | — | 6 | 80 / 10 | `HealSelf 1` |
| 위협 | 갈색 | ✅ | — | 6 | 100 / 0 | `DiscardTargetRandom 1` |
| 휴식 | 갈색 | — | — | 6 | 70 / 10 | `DrawSelf 1` + `RestoreCardUse 1` |
| 약점 포착 | 갈색 | — | — | 6 | 75 / 15 | `ApplyStatus` → 자신 (다음 공격 +1) |
| 함정 | 갈색 | ✅ | — | 6 | 65 / 15 | `ApplyStatus` → 상대 (다음 카드 실패) |
| 준비 | 갈색 | — | — | 4 | 85 / 15 | `ApplyStatus` → 자신 (다음 카드 성공) |
| 대비 | 갈색 | — | — | 4 | 100 / 0 | `ApplyStatus` → 자신 (한도 유지) |
| 드워프 장갑 | 파랑 | — | — | 2 | — | 내 카드가 실패하지 않는다 |

| 요정 갑옷 | 파랑 | — | — | 2 | — | 피격 25% 무효 |

`공격` 열은 `Card.Trait.Attack` 이다 — 용병·무투가가 읽고 AI 규칙 2도 이 열을 본다(E6).
연출(`Card.Trait.Cinematic`)도 같은 두 장(뱅·속공)에 붙어 있다.

**뱅이 20장으로 덱의 27% 다.** 카드 한 종이 이 비중이면 적 행동 분포와 보상 체감이 모두
뱅에 끌려간다 — E5 의 적 덱 구성비 논의와 E8 의 보상 후보 계산이 이 숫자를 전제로 한다.

### 확률 변종

같은 `CardIdTag` 를 쓰는 Row 를 여러 개 둘 수 있다. 데이터 모델이 이미 지원한다.

| 무엇 | 조회 키 | 변종에서 |
|---|---|---|
| 판정 확률·이름·설명·그림·매수 | **Row 이름** | 독립 |
| 덱 전개 (`BuildDeck`) | Row 순회 | 독립 |
| GA 매핑 (`AbilityByCardId`) | `CardIdTag` | 같은 태그 → 같은 GA |
| 효과 (`GA_BGCardEffects`) | `CardIdTag` | **첫 Row 것으로 통일** |

마지막 줄이 제약이자 정의다 — **"효과는 같고 확률만 다른 변종"** 이 지금 가능한 것이고,
그것이 원하는 동작이다. 효과까지 갈라야 하면 GA 페이로드에 Row 이름을 실어야 한다.

Row 이름은 현재 태그 문자열과 1:1 이다. 변종은 접미사를 붙인다.

```
Row 이름                   CardIdTag           확률
Card.Id.Bang           →   Card.Id.Bang        65 / 10
Card.Id.Bang.Precise   →   Card.Id.Bang        80 / 10
Card.Id.Bang.Wild      →   Card.Id.Bang        45 / 25
```

⚠️ `UBGDataSettings::EphemeralAttackCardId` 는 **Row 이름**으로 쓰인다. 규약이 깨진 뒤에는
그 필드가 Row 이름임을 주석으로 명시할 것.

⚠️ **장비 변종은 중복 장착된다.** `HandlePlayCard` 의 중복 검사가 Row 이름을 쓴다
(`HasEquippedCard`). 장비에 변종을 만들 거라면 그 검사를 `CardIdTag` 기준으로 바꾼다.
갈색 카드만 쓸 거면 무관하다.

### 진영별로 나눈다

§16.3 이 이미 "AI 는 전용 덱을 갖는다. 사람과 같은 카드 풀을 쓰지 않아도 된다" 고 적어 뒀다.
공용 덱을 유지하면 보상으로 얻은 카드가 적 손에도 들어가 **성장이 상쇄된다.**

```
현재  ABGGameState::DrawFromDeck(FBGCardInstance& OutCard)          — 덱 하나
필요  ABGGameState::DrawFromDeck(EBGDeckSide Side, FBGCardInstance&) — 플레이어 / 적
```

**좌석별이 아니라 진영별로 둘만 둔다.** 좌석별 덱은 7벌을 셔플·리셔플·복제해야 하고,
적은 어차피 같은 풀을 쓴다. 둘이면 `Deck`/`Discard` 한 쌍이 두 쌍이 될 뿐이다.

⚠️ 시드는 두 덱이 **각자 갖는다.** 하나를 공유하면 적이 뽑는 횟수가 플레이어의 셔플 결과를
밀어 재현이 깨진다 — 판정용 시드를 셔플용과 분리해 둔 것과 같은 이유다(CLAUDE.md 네트워크 항목).

### 진영별 매수 — `PlayerDeckQuantity` / `EnemyDeckQuantity` 최종값

`FBGCardRow`에 진영별 매수 필드를 따로 둔다(PvP 74장 비율을 그대로 축소하는 대신 카드별로
직접 매수를 정하는 쪽으로 결정). 2026-09-03 확정값, `BuildPvEDeck` 로그 기준 Player=16장/Enemy=24장과 일치:

| 카드 | Player | Enemy |
|---|--:|--:|
| 뱅 | 4 | 7 |
| 속공 | 3 | 4 |
| 맥주 | 2 | 2 |
| 위협 | 1 | 2 |
| 휴식 | 2 | 2 |
| 약점 포착 | 1 | 2 |
| 함정 | 1 | 3 |
| 준비 | 1 | 1 |
| 대비 | 1 | 1 |
| 드워프 장갑 / 마녀의 부적 / 요정 갑옷 | 0 | 0 |

설계 근거: 갈색(사용) 카드 9종은 양쪽 다 최소 1장씩 갖는다 — 어느 카드 종류도 한쪽 덱에서
완전히 빠지지 않게 하기 위해서다. 장비(파란 카드)는 조우 보상 경로로만 지급되므로 덱 매수는
양쪽 다 0.

### 카드에 출처를 기록한다

`PushToDiscard(Card)` 의 호출처가 5곳(`ABGGameState` 3 · `ConsumeCard` 1 ·
`GA_BGCardEffects` 1 · `GA_StealOrDiscard` 1)인데 `FBGCardInstance` 에는 출처 정보가 없다.
그리고 `StealTargetRandom` 으로 **카드가 진영을 넘어간다** — 적 덱으로 돌려보내면 훔친 이득이
사라지고, 플레이어 덱에 넣으면 적 카드가 영구 편입되어 성장 상쇄가 반대 방향으로 일어난다.

**`FBGCardInstance` 에 `EBGDeckSide Side` 를 추가한다.** 카드가 출처를 들고 다니면 훔친 카드도
원래 덱으로 돌아간다. `StealTargetEquipRandom`(장비)도 함께 해결된다.

### 적 손패

봇이 좌석을 차지하면 사람과 같은 경로로 손패가 채워진다. E-0 에서 코드를 쓰지 않아도 된다.

| 시점 | 함수 | 장수 |
|---|---|---|
| 판 시작 | `StartMatch()` → `DrawCardsToHand` | `InitialHandSize` 가 0 이면 그 좌석의 체력만큼 |
| 매 턴 | `EnterDrawPhase()` → `DrawCardsToHand` | 어트리뷰트 `DrawCount`, 폴백 2장 |
| 상한 | `GetHandLimitForSeat()` | 좌석 무관 고정 10장 (`MaxHandSize`) |

손패 상한이 현재 체력이라는 원작 규칙은 비활성이다 — 적이 맞을수록 손패가 줄어들지 않는다.
진영별 덱이 바꾸는 것은 **출처 하나**이고, 뽑는 시점·장수·상한은 그대로다.

⚠️ `InitialHandSize` 는 전역 값 하나라 **"플레이어 4장 / 적 3장" 이 불가능하다.** 그리고 기본값
0 이라 체력만큼 준다 — 보스에 체력을 주면 초기 손패가 같이 늘어난다. 진영별 초기 손패가
필요하면 E-3 에서 이 값을 진영별로 쪼갠다.

### 장수

| 덱 | 장수 | 근거 |
|---|--:|---|
| 플레이어 시작 덱 | **16장** | 조우 1회에 2~3회전. 같은 카드가 자주 돌아온다(§16.2) |
| 적 덱 | **24장** | 적 수가 늘어도 한 덱을 나눠 쓴다 |
| 플레이어 덱 상한 | **32장** | 넘으면 원하는 카드가 안 나와 빌드가 흐려진다 |

산출: 조우 1회를 6~8턴으로 잡으면 플레이어 소비량 ≈ 초기 손패 4 + 8턴 × 2 = 20장.
16장 덱이면 조우 중 리셔플이 한 번 돈다 — "덱을 다 보고 다시 본다" 는 감각이 나온다.
PvP 74장은 5인이 나눠 써서 개인당 회전이 훨씬 느리다.

적 덱은 인원수에 비례해 소비된다.

```
조우 1 (적 2명)  초기 8장  + 2명 × 7턴 × 2 = 28장  → 총 36장 / 24장 = 리셔플 1회
조우 6 (적 4명)  초기 16장 + 4명 × 7턴 × 2 = 56장  → 총 72장 / 24장 = 리셔플 3회
```

같은 카드가 돌아오는 것은 §16.3 의 "패턴으로 행동" 에 부합한다. **다만 그 결과로 적 덱 24장의
구성비가 곧 적 행동 분포가 된다** — 뱅 12/24 면 적 행동의 절반이 공격이다.
E7 의 난이도 축에 이것을 포함한다.

### 구성

- **플레이어 시작 덱은 뱅! 과 회복 위주로 좁게.** 시작부터 다양하면 보상 카드가 덱을
  바꾸는 느낌이 안 난다.
- **적 덱에는 장비를 넣지 않는다.** 적 장비는 뽑는 것이 아니라 조우 시작에 장착된 채로
  세운다(E7). 적이 턴을 장비 설치에 쓰면 플레이어가 맞는 횟수만 줄어 지루해진다.

## E6. AI

§16.3 이 정한 원칙 — **"승리 조건이 아니라 패턴으로 행동한다."**

### 두뇌는 컴포넌트 하나

`UBGAIBrainComponent` 를 봇 PlayerController 에 붙인다. 자기 좌석의 턴이 열리면
(`ABGGameState::OnTurnStateChanged`) 손패를 훑어 카드 하나를 고르고
`HandlePlayCard` 를 **직접** 부른다 — 서버 안이라 RPC 가 필요 없다.

### 행동 규칙 — 우선순위 목록 하나

```
1. 체력이 최대의 절반 이하이고 회복 카드가 있으면  → 회복
2. 공격 카드가 있으면                            → 대상 선택 규칙으로 대상을 정해 사용
3. 그 밖에 쓸 수 있는 카드가 있으면               → 무작위로 1장
4. 없으면                                        → 턴 종료
```

카드 사용 한도(기본 2장)만큼 반복한다. **상태 기계도 행동 트리도 쓰지 않는다** —
규칙이 네 줄이면 그 둘은 읽기만 어렵게 만든다. 규칙이 늘어나면 그때 옮긴다.

기댓값 점수 방식(카드마다 `Op × Amount × 등급확률` 로 점수를 매겨 최고점을 고르는 것)은
채택하지 않는다. 아래 "확률을 읽히지 않는다" 와 같은 이유다.

### 카드 분류

- **회복 카드** = `OutcomeEffects` 에 `HealSelf` 가 있는 카드
- **공격 카드** = `TraitTags` 에 `Card.Trait.Attack` 이 있는 카드 (현재 뱅·속공)

공격 카드는 태그로 판정한다. `Card-Data-Spec.md` 가 "함정은 대상을 고르지만 공격이 아니다" 로
경계를 그어 뒀고, 그 경계가 규칙 2·3 의 갈림과 정확히 같다 — 함정은 규칙 3(무작위)으로 가는
것이 맞다. 용병·무투가가 읽는 것과 같은 태그를 쓰므로 판정 기준이 두 곳으로 갈리지 않는다.

### 규칙이 현재 12종에 걸리는 결과

| 규칙 | 해당 카드 | 비중 (덱 74장 기준) |
|---|---|--:|
| 1. 회복 | 맥주 | 6장 = **8%** |
| 2. 공격 | 뱅 · 속공 | 30장 = **41%** |
| 3. 무작위 | 위협 · 함정 · 휴식 · 약점 포착 · 준비 · 대비 · 장비 3종 | 38장 = 51% |

- **회복 카드가 맥주 하나뿐이다.** 규칙 1의 발동률이 8% 라 적이 회복하는 장면을 거의 못 본다.
  E7 의 "집중 공격의 압박" 은 플레이어 쪽에만 걸리고, 적 쪽 회복은 사실상 없는 규칙이다.
- **반면 규칙 2가 41% 다.** 뱅 20장·속공 10장이라 적 행동의 절반 가까이가 공격이다.
  적 덱을 74장 풀에서 그대로 뽑으면 조우 1부터 계속 맞는다 — E5 의 적 덱 구성으로
  공격 비중을 낮추는 것이 성격·직업보다 먼저 손대야 할 손잡이다.
- **AI 는 콤보를 하지 않는다.** 약점 포착·준비를 쓰고 다음 턴에 뱅!을 내는 조합은 규칙 3의
  무작위에 묻힌다. §16.3 에 부합하지만, 콤보를 원하면 규칙을 늘리는 것이 아니라
  **적 덱 구성비**로 유도한다(약점 포착을 적 덱에서 빼면 그 문제가 사라진다).

### 사용이 성사됐는지 확인한다

`HandlePlayCard` 는 `void` 이고, 거부할 때 로그만 남기고 `return` 한다. 게이트가 8개 있다 —
턴/페이즈 · 사용 한도 · 대상 생존 · ASC · 손패 존재 · GA 매핑 · 상태 중첩 · 장비 중복.

거부를 감지하지 못하면 "사용 한도만큼 반복" 이 무한 루프가 되거나 턴이 멈춘다.

**호출 전후로 `PS->GetCardsUsedThisTurn()` 을 비교한다.** 성사되지 않은 카드는 후보에서 빼고
다음으로 넘어간다.

장기적으로는 게이트를 `CanPlayCard(InstanceId, TargetSeat, FText& OutReason) const` 로 추출한다.
사람 UI 도 카드 한 장 단위로 사용 가능 여부를 계산할 수 있게 된다(현재
`UpdateHandInteractionLock` 은 손패 전체 단위로만 잠근다). **E-5 에서 추출한다** —
대상 지정·장비까지 넓히면 게이트 3·7·8 이 필요해진다.

### 대상 선택 — 적의 성격

| 성격 | 대상 | 성격이 만드는 압박 |
|---|---|---|
| 공격형 | 체력이 가장 낮은 적 | 맞기 시작하면 계속 맞는다 — 회복 타이밍을 강제한다 |
| 방해형 | 손패가 가장 많은 적 | 패를 모으는 플레이를 벌한다 |
| 무작위 | 균등 | 초반 조우용. 예측 부담이 없다 |

성격은 `FBGCharacterRow`(직업 DT)에 얹는다. 직업 시스템을 그대로 쓰므로 적 전용
스탯 체계가 필요 없다 — §16.2 의 근거와 같은 논리다.

난이도는 **성격 + 규칙 발동 임계값 + 규칙 3의 선택 가중치** 로 조절하고, 판정 확률 자체는
장비로 올린다(E7).

### ⚠️ AI 에게 확률을 읽히지 않는다

`UBGDiceComponent::ApplyModifiers` 로 최종 확률을 계산해 최적 카드를 고르게 하면
**AI 가 사람보다 강해진다.** 사람은 카드 UI 에 뜬 숫자를 보고 판단하지만 그것도 한 장씩이다.
AI 는 손패 전체를 동시에 비교할 수 있어 같은 정보로도 우위를 갖는다.

패턴은 **손패의 종류와 체력만** 본다. 판정 결과는 사람과 똑같이 서버가 굴린다.

### 밧줄

AI 턴에는 밧줄을 붙이지 않는다(`Rope->BeginRope` 를 건너뛴다). 제한 시간은 사람이
고민하느라 판을 세우는 것을 막는 장치인데, AI 는 즉시 결정한다.

대신 **AI 턴에 최소 대기 시간을 둔다.** 카드를 즉시 내면 무슨 일이 일어났는지 읽히지 않는다.
연출이 있는 카드는 연출 길이가 그 역할을 하지만, 연출 없는 카드에는 별도 지연이 필요하다.

⚠️ `Card.Trait.Cinematic` 은 **일부 카드에만 붙어 있다**(뱅에는 있다). 연출이 없는 카드로만
턴이 돌면 봇 4명이 순식간에 넘어가 플레이어가 무슨 일이 일어났는지 보지 못하므로,
대기 시간은 연출 유무와 무관하게 **항상 최소값을 보장한다** — 연출이 있으면 그 길이가
최소값을 넘으므로 자연히 연출 쪽이 이긴다.

⚠️ **밧줄 스킵은 E-2 부터 적용한다.** E-0·E-1 의 봇은 두뇌가 없어 스스로 턴을 끝내지 못하므로,
그 단계에서 밧줄을 떼면 판이 영구 정지한다.

## E7. 적 구성과 강화

§16.1 이 정한 두 축 — **적 수 늘리기 + 기본 장비 장착.**
여기에 **적 덱 구성비**(E5)와 **적 직업**이 더해져 난이도 축은 넷이다.

### 배분안

**2026-09-03 좌석 배분 잠정안 (아래 표가 배분안을 대체한다 — 아직 튜닝 중, 바뀔 수 있다):**

| 조우 | 총 좌석 | 구성 | 적 장비 | 성격 | 의도 |
|--:|--:|---|---|---|---|
| 1 | 2 | 1대1 | 미구현 (E-5) | 미구현 (E-5) | 기본 루프 학습 |
| 2 | 3 | 1대2 | 미구현 (E-5) | 미구현 (E-5) | |
| 3 | 5 | 2대3 (부관 1 등장) | 미구현 (E-5) | 미구현 (E-5) | |
| 4 | 6 | 2대4 | 미구현 (E-5) | 미구현 (E-5) | |
| 5 이후 (`MaxPlayers`=7 고정) | 7 | 3대4 (사람+부관2 vs 무법자4) | 미구현 (E-5) | 미구현 (E-5) | 7인전 BANG 표 그대로, 이후 난이도는 장비·성격(E-5)로만 조정 |

조우5부터는 좌석을 7로 고정하고 난이도는 장비·성격으로만 올리는 안이다. `UBGMatchStartComponent::ComputeTargetSeatsForEncounter`
가 위 표를 지금 그대로 구현하고 있지만, **이 좌석 배분 자체가 아직 플레이테스트로 튜닝 중인 잠정안**이라
표 값은 언제든 바뀔 수 있다. 적 장비·성격 배분(E-5)은 아직 설계·구현 모두 착수 전이다.

### PvE 최소 인원을 2 로 내린다

기존 최소 인원 4는 GetMinStartPlayers()/CanStartMatch()/AssignRoles()/AssignJobs() 네 곳에 독립적으로 걸려 있다. AssignRoles/AssignJobs는 PvE 전용 배정 경로(E3)가 그 함수를 타지 않아 우회되고, CanStartMatch()은 E-0 범위다. 실제 수정은 GetMinStartPlayers() 한 곳.

`MaxPlayers = 7` 은 그대로 둔다 — **PvE 최대도 7좌석이다**

### 조우별 적 직업 화이트리스트

`AssignJobs` 는 직업 12종을 셔플해 균등 배정한다. 그대로 쓰면 조우 1의 "무작위" 적이 용병이나
암살자를 뽑아 "기본 루프 학습" 의도가 무너진다. **직업은 성격보다 센 축이다** — 성격은 대상
선택만 바꾸지만 직업은 판정 확률과 행동 횟수 자체를 바꾼다.

| 직업 | 적에게 갔을 때 | 조우 1~2 |
|---|---|:--:|
| 용병 | 공격 카드가 실패하지 않는다 | ❌ |
| 암살자 | 대성공마다 1회성 공격 카드 — 공격이 연쇄한다 | ❌ |
| 무투가 | 50% 로 사용한도 미소모 — 턴에 3~4장 | ❌ |
| 수도사 | 때릴 때마다 플레이어가 반사 피해 | ❌ |
| 사냥꾼 | `CardUseLimit` 3 | ⚠️ |
| 마법사 | 50% 로 피해 +1 | ⚠️ |
| 기사 · 수색꾼 · 사제 · 치유사 · 점술가 · 도둑 | 조우가 길어지거나 손패가 도는 정도 | ✅ |

### 조우별 허용 직업 (초안)

E3 의 PvE 전용 배정 경로가 이 목록에서 뽑는다.

| 조우 | 적 수 | 뽑을 수 있는 직업 | 의도 |
|--:|--:|---|---|
| 1 | 1 | 기사 · 수색꾼 | 순한 적. 규칙만 익힌다 |
| 2 | 2 | + 사제 · 치유사 | 회복하는 적 — 딜을 몰아야 함을 배운다 |
| 3 | 3 | + 점술가 · 도둑 | 손패가 털리기 시작한다 |
| 4 | 4 | + 사냥꾼 · 마법사 | 적이 더 많이·더 세게 때린다 |
| 5 | 4 | + 수도사 · 무투가 | 반사·연타 |
| 6 (보스) | 4 | 전체 12종 | 최종 |

적 수는 E7 "배분안" 의 2026-09-03 좌석 배분 잠정안(총 좌석 기준) 을 따른다 — 조우5 이후는
좌석이 7로 고정되어 적 수도 4에서 더 늘지 않는다. 이 잠정안이 바뀌면 아래 표도 같이 바뀐다.

원칙 둘이다.

- **누적한다.** 뒤 조우는 앞 조우의 직업을 포함한다 — 그래야 학습이 쌓인다.
- **강한 4종은 뒤로 미룬다.** 용병·암살자·무투가·수도사는 조우 5 이후에만 나온다.

⚠️ **이 표는 실측 전 추측이다.** 위 4종이 실제로 얼마나 아픈지는 E-5 에서 붙여 봐야 안다.
난이도 곡선 튜닝이므로 플레이 테스트로 조정한다 — E9 의 측정 지표에 포함했다.

**밸런스 참고(강제 규칙 아님):** 용병(공격 판정이 실패하지 않음)과 암살자(대성공마다
공격 카드가 추가됨)는 둘 다 "공격이 확실하고 잦아진다"는 같은 축이라, 조우6(보스)에서
둘 다 뽑히면 체감 난이도가 특히 튈 수 있다. 코드에서 강제로 막지는 않는다 — 실제
플레이테스트로 문제가 확인되면 그때 조우6 화이트리스트에 캡을 다시 건다.

⚠️ 용병·무투가는 **지금 이미 동작한다**(`Card.Trait.Attack` 이 뱅·속공에 들어가 있다).
화이트리스트 없이 E-5 를 켜면 조우 1부터 그 둘이 나올 수 있으므로, 배정 경로와 목록을
같은 단계에서 함께 넣는다.

### 적 장비

⚠️ **실제로 쓸 수 있는 장비가 2종뿐이다.** 요정 갑옷이 0장이라 드워프 장갑·마녀의 부적 둘뿐이고,
장비 배분 수량은 아직 미정(E-5)이지만 조우 6(보스)처럼 적 전원에게 장비를 채우려 하면
2종 중에서 고를 수밖에 없어 같은 조합이 반복된다 — 조우마다 다른 문제를 준다는 취지가
사라진다. 그리고 그 2종 중 하나가 마녀의 부적이라 점술가 적에게
배정되면 승산 ×4 가 거의 확정된다(E10). **화이트리스트가 직업과 장비를 함께 배정해야 한다.**

장비 종류를 늘리는 것이 곧은 해법이고, 요정 갑옷에 매수를 넣는 것이 가장 싼 첫 수다
(`Card-Data-Spec.md` 에 따르면 방어 판정은 이미 구현되어 있고 `QuantityOfCard` 만 올리면 된다).
장비는 확률 변종으로 늘릴 수 없다 — 효과가 태그로 조회되므로 **새 태그**가 필요하다(E5).

**화이트리스트는 "점술가 적에게 마녀의 부적을 주지 않는다" 를 포함한다.** 둘이 겹치면 승산이
×4 가 되고(E10), 장비가 2종뿐인 지금은 우연이 아니라 구조적으로 발생한다.

⚠️ **적 장비의 `InstanceId` 발급 지점이 없다.** `EquipCard` 는 `FBGCardInstance` 를 요구하는데
덱에서 뽑지 않는 장비는 ID 를 새로 만들어야 한다. ID 공간이 이미 둘로 나뉘어 있다.

```
덱에서 나온 카드    1 부터 양수
1회성 카드(암살자)  -2 부터 음수   (bEphemeral = true)
```

적 장비는 셋째 경우다. 음수 카운터(`NextEphemeralInstanceId`)를 재사용하고 `bEphemeral = false`
로 두되, **발급 지점을 한 곳으로 모은다.** 지금은 `GrantEphemeralCards` 안에만 있다.

### ⚠️ 체력으로 강화하지 않는다

적 체력을 올리는 것이 가장 쉬운 손잡이지만, §16.2 가 장비 강화를 택한 근거
("장비 카드 시스템을 그대로 쓸 수 있다")를 버리는 선택이다. 체력을 올리면 조우가 길어질 뿐
플레이어가 마주하는 **문제의 종류가 바뀌지 않는다.** 장비는 확률 축을 바꾸므로
플레이어의 대응도 바뀐다.

그리고 적 체력은 초기 손패와 묶여 있다(E5) — 체력을 올리면 손패도 늘어난다.
보스만 예외로 둘 수 있으나, 그때도 체력이 아니라 **장비 2장 + 성격** 으로 먼저 시도한다.

## E9. 구현 단계

각 단계는 **그 단계만으로 검증 가능해야** 한다. AI 를 다 만든 뒤에 켜 보는 방식이면
어디서 틀렸는지 알 수 없다.

| 단계 | 내용 | 총 좌석 | 검증 |
|---|---|--:|---|
| **E-0** | 봇 PC 스폰 — 좌석만 채우고 아무 행동 안 함. 밧줄은 그대로 붙인다 | 2 | PvE 로 열면 판이 시작된다. 봇 턴은 밧줄 만료로 넘어간다. 봇이 HUD 를 만들지 않는다 |
| **E-1** | PvE 전용 역할·직업 배정 (사람=보안관, 봇=무법자) | 2 | 봇을 죽이면 승리, 플레이어가 죽으면 패배로 표시된다 |
| **E-2** | `UBGAIBrainComponent` — 규칙 4줄. 밧줄 스킵 + 최소 대기 시간 | 3~4 | 봇이 자기 턴에 뱅!을 쓰고 연출이 돈다. 거부된 카드로 턴이 멈추지 않는다 |
| **E-3** | 진영별 덱 + `FBGCardInstance.Side` + 진영별 초기 손패 | 4 | 적이 전용 덱에서 뽑는다. `BG_DumpDeck` 이 두 덱을 찍는다. 훔친 카드가 원래 덱으로 돌아간다 |
| **E-4** | 조우 리셋 경로 + 보상 → 다음 조우 | 4 | 3조우를 이어서 진행하고 체력이 조우마다 리셋된다. 덱·장비 지속 여부는 미정 — E4 표 참조 |
| **E-5** | 적 장비·직업 배분 · 성격 · `CanPlayCard` 추출 | 3~5 | E7 표대로 난이도가 오른다 |

**E-0 과 E-1 이 가장 위험하다.** 봇 PC 가 HUD 를 만들거나(E2 의 함정) 역할 배정이
`CheckWinCondition` 과 어긋나면 그 위의 모든 단계가 흔들린다. 이 둘을 먼저 못 박을 것.

### E-0 의 수정 범위

| 파일 | 무엇 |
|---|---|
| `BGGameMode.h/.cpp` | `SpawnAIPlayers()` + `AIControllerClass` 프로퍼티 추가 |

## E10. 미결정으로 남기는 것

이 문서로 답하지 않는다. **플레이 테스트 없이 정하면 근거가 없다.**

- **런 길이** — 조우 6회를 가정했으나 근거는 없다. E-4 이후 실측한다.
- **실패 시 처리** — 런 처음부터 / 마지막 조우 재시도 / 진행도 일부 유지.
  Slay the Spire 는 처음부터지만, 그건 런 하나가 40분이라 성립한다. BAAM 조우가
  얼마나 걸리는지 먼저 재야 한다.
- **런 중간 저장** — 필요 여부가 런 길이에 달려 있다.
  ⚠️ 전제: **런 상태를 담을 곳이 없다.** `ABGGameInstance` 는 세션 전용이고 덱 구성·체력·장비를
  들고 있지 않다. 저장·실패 재시도·로비 복귀 중 어느 것이든 트래블을 요구하면
  `UBGGameInstance` 나 SaveGame 에 보관소를 새로 만들어야 한다.
- **점술가 + 마녀의 부적** — **메인 기획자 판단(PvP 밸런스)**. 둘이 방식도 값도 같아
  (각각 대성공·대실패 승산 ×2) 함께 쓰면 ×4 가 된다. 뱅! 기준으로:

  | | 대실패 | 실패 | 성공 | 대성공 |
  |---|--:|--:|--:|--:|
  | 일반 | 5% | 20% | 65% | 10% |
  | 점술가 **또는** 부적 | 9% | 18% | 55% | 18% |
  | 점술가 **+** 부적 | 15% | 15% | 45% | 25% |

  선택지는 ⓐ 허용(코드 0줄, 하이리스크 빌드로 성립) ⓑ 중첩 차단(GE 에 태그 검사 — PvP 코드
  수정) ⓒ 부적 값 하향(데이터만, 단독 사용감도 바뀐다) 이다. `Character-List.csv` 의 점술가
  비고가 이 항목을 미결정으로 남겨 뒀다.

  ⚠️ **PvE 는 이 결정을 기다리지 않는다.** 어느 쪽으로 정해지든 E7 의 화이트리스트가
  "점술가 적에게는 부적을 주지 않는다" 를 지키면 PvE 에서는 ×4 가 발생하지 않는다.
  구조적으로 발생하는 이유는 쓸 수 있는 장비가 2종뿐이어서 조우 6 의 적 전원이 장갑+부적을
  끼게 되기 때문이다(E7) — 장비 종류가 늘면 이 압력도 줄어든다.
- **런에 등장시킬 직업 범위** — 배정은 균등 1/N 이고 빈도 가중치를 두지 않기로 했다.
  그런데 한 판 최대 7인에 직업이 12종이라 **절반 가까이가 등장하지 않는 판이 나온다.**
  PvP 에서는 다양성이지만, 런을 이어 가는 PvE 에서는 "이번 런에 그 직업을 못 봤다" 가
  된다. 런 단위로 후보를 고정할지 조우마다 다시 뽑을지 정해야 한다.
- **직업 메쉬와 역할 외형의 우선순위** — 아트 기획서가 외형을 **역할**에 묶어 뒀다
  (인간=부관 / **마족=무법자** / 배신자). PvE 의 적은 전부 `Role.Outlaw` 이므로 자동으로
  마족이고, **적 전용 직업 축은 필요하지 않다.**
  남은 것은 직업 전용 메쉬가 들어온 뒤의 우선순위다 — 직업 메쉬와 역할 외형이 충돌할 때
  어느 쪽이 이기는가. 현재 `Character-List.csv` 의 `SkeletalMesh` 는 12종 전부 `(미정)` 이라
  전원 기본 메쉬를 쓰므로 **지금은 문제가 되지 않고 E-5 를 막지 않는다.**

## E11. 선행 과제

PvE 를 시작하기 전에 PvP 쪽에서 끝나 있어야 하는 것.

| 과제 | 상태 |
|---|---|
| 직업 12종 능력 **코드** 구현 | ✅ 완료 |
| 공격·회복 보정 어트리뷰트 | ✅ 완료 |
| `Card.Trait.Attack` 태깅 | ✅ 완료 — 뱅·속공에 들어가 있다 (`Card-Data-Spec.md` 가 정한 대상과 일치) |
| `Card.Trait.Cinematic` 확대 적용 | ⬜ 아트 진행에 달렸다 — 뱅에는 붙어 있고, 나머지 카드는 연출 애셋이 나오는 대로 |
| `DT_BGCard.json` ↔ uasset 정합 | ⬜ 남음 — **어긋나 있다.** Row 는 양쪽 12개로 같지만 uasset 의 `TraitTags`(`Attack`·`Cinematic`)가 JSON 에 반영되지 않았다. 에디터에서 JSON 을 다시 export 하면 끝난다 |

§16 이 "PvP 규칙이 검증된 뒤에 시작한다" 고 못박은 조건은 직업·어트리뷰트 쪽은 충족되었고
**카드 데이터 쪽 두 항목이 남았다.** 둘 다 E-3 전까지 끝나면 되고, **E-0 과 E-1 은 무관하다** —
봇이 좌석을 채우고 역할을 받는 것까지는 카드 데이터와 상관이 없다.

### ⚠️ 카드 데이터의 정본은 uasset 이다

`Docs/Data/DT_BGCard.json` 은 **낡은 스냅샷이다** — 매수(뱅 12 vs 20)와 `TraitTags`
(`Attack`·`Cinematic`)가 uasset 과 다르다. 카드 데이터를 확인할 때는 에디터의 `DT_BGCard` 나
`BG_DumpDeck` 을 본다.

⚠️ **낡은 JSON 을 재임포트하지 말 것.** 임포트 절차는 "기존 행을 전부 교체" 하므로
매수와 태깅이 모두 되돌아간다.

2026-08-24 에 에디터에서 export 한 최신 스냅샷이 **`Docs/Data/DT_BaamCard.json`** 에 있다
(애셋에 저장된 소스 경로가 옛 이름이라 그 파일명으로 나갔다). 정합을 닫으려면 이 파일을
`DT_BGCard.json` 자리로 정리해야 하는데, **export 형식이 임포트 형식과 다르다** —
UTF-16 인코딩이고 표시 문자열이 `NSLOCTEXT(...)` 로 감싸여 있다. 그대로 덮어쓰면 임포트
경로가 깨질 수 있으므로, 옮기기 전에 임포트가 되는지 확인할 것.

### 직업 구현 현황 (2026-08-24)

정본은 `Docs/Data/Character-List.csv` 다. **12종 전부 동작한다.**

| 직업 | 능력 | PvE 에서 적에게 갔을 때 |
|---|---|---|
| 기사 | MaxHealth 5 | 조우가 길어진다 |
| 사냥꾼 | `CardUseLimit` 3 | 턴에 3장 낸다 |
| 수색꾼 | `DrawCount` 3 | 손패가 마르지 않는다 |
| 점술가 | 승산 대성공·대실패 ×2 | 마녀의 부적과 겹치면 ×4 |
| 사제 | 회복 +1 | 적 회복이 늘어난다 |
| 치유사 | 턴 시작 회복 1 / MaxHealth 3 | 딜을 넣다 말면 되돌아온다 |
| 마법사 | 공격 시 50% 로 피해 +1 | 실질 피해 1.5배 |
| 수도사 | 피해 반사 1 / MaxHealth 3 | 때릴 때마다 플레이어가 맞는다 |
| 용병 | 공격 카드 실패 비율 −1000 | 적 공격이 실패하지 않는다 |
| 무투가 | 공격 시 50% 로 사용한도 미소모 | 턴에 3~4장 낸다 |
| 도둑 | 피해 받을 때 가해자 카드 1장 강탈 | 플레이어 손패가 마른다 |

드로우 보정은 목록에서 뺐다 — 수색꾼이 요구하는 "매 턴 1장 더" 는 기존 `DrawCount` 로
이미 해결된다. 남은 것은 카드 효과의 `DrawSelf` 보정인데 이를 요구하는 직업이 없다.
