# BAAM PvE 모드 기획서

`Game-Design-Document.md` **§16 의 하위 문서**다. 상위 규칙(판정·턴·카드·장비)은 GDD 가 정본이고,
이 문서는 §16.5 가 미결정으로 남긴 항목을 구체화한다. **PvP 규칙은 이 문서로 바뀌지 않는다.**

> 섹션 번호를 GDD 와 겹치지 않게 `E` 로 시작한다 — 코드 주석이 GDD 번호(§4.2 · §13.1 등)를
> 직접 참조하고 있어, 두 문서가 같은 번호를 쓰면 어느 쪽을 가리키는지 알 수 없어진다.

---

## E1. 설계 전제

§16 이 못박은 전제는 하나다. **새 게임 로직을 만들지 않는다.**

이 전제는 장식이 아니라 예산이다. PvE 를 "다른 게임" 으로 만들면 카드 31종·판정·장비·연출을
두 벌 유지해야 하고, PvP 에 카드를 하나 추가할 때마다 PvE 쪽을 함께 고쳐야 한다.
그래서 이 문서의 모든 제안은 다음 질문을 통과해야 한다.

> **이것을 PvP 코드를 고치지 않고 만들 수 있는가?**

통과하지 못하는 항목은 E3(역할)·E5(덱)에 **명시적으로 표시**했다. 지금 시점에서
PvE 가 요구하는 구조 변경은 그 둘뿐이다.

### 재활용되는 것

| 시스템 | 그대로 쓰는가 | 근거 |
|---|---|---|
| 4단계 확률 판정 | ✅ 손대지 않음 | 서버 권위라 행동 주체가 사람이든 AI 든 같다 |
| 카드 효과 (`OutcomeEffects`) | ✅ | 데이터라 모드를 모른다 |
| 장비 (파란 카드) | ✅ | 적 강화를 장비로 푸는 근거 (§16.2) |
| 좌석·턴 진행 | ✅ | `CanSeatPlayCards` 가 좌석 기준이다 |
| 승패 판정 | ✅ | E3 의 역할 고정 배정으로 그대로 성립한다 |
| 연출 (카드·사망) | ✅ | `ABGGameState` 의 단계 축이 좌석을 모른다 |
| 밧줄 (제한 시간) | ⚠️ 조정 | AI 턴에는 붙일 이유가 없다 — E6 참고 |

## E2. 지금 코드가 PvE 를 막는 지점

§16.4 는 "AI 미구현" 이라고만 적혀 있는데, 실제로 걸리는 것은 AI 알고리즘이 아니라
**좌석을 차지하는 주체**다.

```
UBGSeatComponent::AssignSeatOnJoin(APlayerController* NewPlayer)
                                   ^^^^^^^^^^^^^^^^^ 좌석은 PlayerController 에 묶여 있다

ABGPlayerController::HandlePlayCard(InstanceId, TargetSeat)
^^^^^^^^^^^^^^^^^^^ 카드 사용 규칙 전체(검증·판정·GA 발동·연출 시작)가 여기 있다
```

즉 **PlayerController 가 없으면 카드를 낼 수 없다.** 반대로 `ABGPlayerState` 는
손패·장비·좌석의 정본이고 `ABGGameState::CanSeatPlayCards(Seat)` 는 좌석 번호만 보므로,
그 둘은 AI 에게도 그대로 쓸 수 있다.

### 두 갈래

**(A) 봇 PlayerController 를 스폰한다** — 연결 없는 `ABGPlayerController` 를 서버가 직접 만든다.
좌석·손패·카드 사용 경로를 **한 줄도 고치지 않는다.**

**(B) `HandlePlayCard` 를 GameState/GameMode 로 옮긴다** — 구조상으로는 이쪽이 옳다.
카드 사용은 규칙이지 입력이 아니다. 하지만 PvP 의 검증된 경로를 통째로 건드린다.

### 권고: (A) 를 먼저

E1 의 전제를 코드 수준에서도 지키는 쪽이다. (B) 는 PvP 가 안정된 뒤 P2 이후 리팩터로 남긴다 —
그때 옮기더라도 봇은 얇은 호출자만 바꾸면 되므로 (A) 가 (B) 를 막지 않는다.

⚠️ **(A) 의 함정**: `ABGPlayerController` 에는 위젯 생성·입력 바인딩·뷰타깃 코드가 있다.
봇 PC 에서 그게 돌면 화면 없는 컨트롤러가 HUD 를 만든다. 이미 `IsLocalController()` 로
막혀 있는 곳(`HandleCameraShotChanged` 등)이 있으니, **봇을 붙이기 전에 그 가드가
빠진 곳을 먼저 훑어야 한다.** 빠뜨리면 봇 수만큼 HUD 가 겹쳐 뜬다.

## E3. 역할 — 제거하지 않고 고정 배정한다

§16.5 의 첫 미결정. "역할 시스템을 PvE 에서 어떻게 다룰지 (제거 / 단순화 / 유지)".

### 결론: 유지하되 배정을 고정한다

| 좌석 | 역할 | 서사 |
|---|---|---|
| 플레이어 | `Role.Sheriff` | 용사 |
| AI 전부 | `Role.Outlaw` | 마왕군 |

**`CheckWinCondition` 을 한 줄도 고치지 않아도 그대로 맞는다.**

```
보안관 사망            → 무법자 승  =  플레이어 패배  ✅
무법자·배신자 전멸      → 보안관 승  =  플레이어 승리  ✅
```

역할을 제거하는 쪽이 직관적으로 보이지만, 그러면 승패 판정을 PvE 전용으로 새로 써야 한다 —
E1 의 전제를 첫 항목부터 어긴다. 배정만 바꾸면 규칙 코드가 통째로 재활용된다.

### 부관과 배신자

- **부관은 쓰지 않는다.** 아군 AI 를 넣으면 "보안관이 부관을 쏘면 전 재산 몰수" 라는
  원작 벌칙이 살아나는데, PvE 에서 그 규칙은 학습 대상이 아니라 사고다.
- **배신자는 후반 레벨의 변주로 남긴다.** 적 하나를 `Role.Renegade` 로 두면 마지막 1인이
  됐을 때 승리 조건이 갈린다 — 코드 변경 없이 난이도 축이 하나 늘어난다.
  다만 E7 의 레벨 표에서 **선택 항목**으로 둔다(먼저 검증할 것이 아니다).

### 은닉은 하지 않는다

역할 은닉은 사람이 상대일 때만 재미가 된다(§16.2 가 이미 인정). PvE 에서는
적의 역할을 처음부터 공개한다 — `ABGPlayerState::SetPublicRole` 을 판 시작에 부르면 된다.

## E4. 한 판의 구조

```
런 시작 → 직업 선택 → [조우 1] → 보상 → [조우 2] → 보상 → … → [보스 조우] → 런 종료
                        └ 기존 BAAM 한 판 그대로 (판정·턴·연출 전부 동일)
```

- **조우(Encounter) = 기존 BAAM 한 판.** 레벨이라는 말 대신 조우를 쓴다 —
  "레벨" 은 UE 의 맵과 헷갈린다.
- 조우가 끝나면 맵을 갈아엎지 않는다. 같은 모닥불 자리에서 적만 새로 세운다.
  아트 기획서의 "모닥불 중심 원형 배치" 가 그대로 유지되고, 레벨 로딩이 없어 회전이 빠르다.

### 조우 사이에 이어지는 것 / 리셋되는 것

| | 이어짐 | 근거 |
|---|:--:|---|
| 플레이어 덱 (획득 카드) | ✅ | 이게 성장이다 |
| 플레이어 장비 | ✅ | 빌드가 조우 하나로 끝나면 장비를 고를 이유가 없다 |
| 플레이어 체력 | ✅ | 자원 관리가 런의 긴장이다 |
| 손패 | ❌ 리셋 | 조우마다 새로 뽑는다 |
| 적 전부 | ❌ | 조우마다 새로 세운다 |

⚠️ 체력을 이어가면 **회복 카드의 가치가 조우 안이 아니라 런 전체에서 매겨진다.**
이건 의도된 설계지만, 회복이 부족하면 런이 3조우에서 끝나고 넘치면 긴장이 사라진다.
E9 의 첫 측정 대상이다.

## E5. 덱

§16.5 의 미결정 "PvE 덱의 구체적인 장수와 구성".

### 진영별로 나눈다 — PvE 가 요구하는 유일한 구조 변경

§16.3 이 이미 "AI 는 전용 덱을 갖는다. 사람과 같은 카드 풀을 쓰지 않아도 된다" 고 적어 뒀다.
공용 덱을 유지하면 보상으로 얻은 카드가 적 손에도 들어가 **성장이 상쇄된다.**

```
현재  ABGGameState::DrawFromDeck(FBGCardInstance& OutCard)          — 덱 하나
필요  ABGGameState::DrawFromDeck(EBGDeckSide Side, FBGCardInstance&) — 플레이어 / 적
```

**좌석별이 아니라 진영별로 둘만 둔다.** 좌석별 덱은 7벌을 셔플·리셔플·복제해야 하고,
적은 어차피 같은 풀을 쓴다. 둘이면 `Deck`/`Discard` 한 쌍이 두 쌍이 될 뿐이다.

⚠️ 시드는 두 덱이 **각자 갖는다.** 하나를 공유하면 적이 뽑는 횟수가 플레이어의 셔플 결과를
밀어 재현이 깨진다 — 판정용 시드를 셔플용과 분리해 둔 것과 같은 이유다(CLAUDE.md 네트워크 항목).

### 장수

| 덱 | 장수 | 근거 |
|---|--:|---|
| 플레이어 시작 덱 | **16장** | 조우 1회에 2~3회전. 같은 카드가 자주 돌아온다(§16.2) |
| 적 덱 | **24장** | 적 수가 늘어도 한 덱을 나눠 쓴다 |
| 플레이어 덱 상한 | **32장** | 넘으면 원하는 카드가 안 나와 빌드가 흐려진다 |

산출: 조우 1회를 6~8턴으로 잡으면 플레이어 소비량 ≈ 초기 손패 4 + 8턴 × 2 = 20장.
16장 덱이면 조우 중 리셔플이 한 번 돈다 — "덱을 다 보고 다시 본다" 는 감각이 나온다.
PvP 64장은 5인이 나눠 써서 개인당 회전이 훨씬 느리다.

### 구성

- **플레이어 시작 덱은 뱅! 과 회복 위주로 좁게.** 시작부터 다양하면 보상 카드가 덱을
  바꾸는 느낌이 안 난다.
- **적 덱에는 장비를 넣지 않는다.** 적 장비는 뽑는 것이 아니라 조우 시작에 장착된 채로
  세운다(E7). 적이 턴을 장비 설치에 쓰면 플레이어가 맞는 횟수만 줄어 지루해진다.

## E6. AI

§16.3 이 정한 원칙 — **"승리 조건이 아니라 패턴으로 행동한다."**

### 두뇌는 컴포넌트 하나

`UBGAIBrainComponent` 를 봇 PlayerController 에 붙인다. 자기 좌석의 턴이 열리면
(`ABGGameState::OnTurnStateChanged`) 손패를 훑어 카드 하나를 고르고
`HandlePlayCard` 를 **직접** 부른다 — 서버 안이라 RPC 가 필요 없다.

### 행동 규칙 — 우선순위 목록 하나

```
1. 체력이 최대의 절반 이하이고 회복 카드가 있으면  → 회복
2. 공격 카드가 있으면                            → 대상 선택 규칙으로 대상을 정해 사용
3. 그 밖에 쓸 수 있는 카드가 있으면               → 무작위로 1장
4. 없으면                                        → 턴 종료
```

카드 사용 한도(기본 2장)만큼 반복한다. **상태 기계도 행동 트리도 쓰지 않는다** —
규칙이 네 줄이면 그 둘은 읽기만 어렵게 만든다. 규칙이 늘어나면 그때 옮긴다.

### 대상 선택 — 적의 성격

| 성격 | 대상 | 성격이 만드는 압박 |
|---|---|---|
| 공격형 | 체력이 가장 낮은 적 | 맞기 시작하면 계속 맞는다 — 회복 타이밍을 강제한다 |
| 방해형 | 손패가 가장 많은 적 | 패를 모으는 플레이를 벌한다 |
| 무작위 | 균등 | 초반 조우용. 예측 부담이 없다 |

성격은 `FBGCharacterRow`(직업 DT)에 얹는다. 직업 시스템을 그대로 쓰므로 적 전용
스탯 체계가 필요 없다 — §16.2 의 근거와 같은 논리다.

### ⚠️ AI 에게 확률을 읽히지 않는다

`UBGDiceComponent::ApplyModifiers` 로 최종 확률을 계산해 최적 카드를 고르게 하면
**AI 가 사람보다 강해진다.** 사람은 카드 UI 에 뜬 숫자를 보고 판단하지만 그것도 한 장씩이다.
AI 는 손패 전체를 동시에 비교할 수 있어 같은 정보로도 우위를 갖는다.

패턴은 **손패의 종류와 체력만** 본다. 판정 결과는 사람과 똑같이 서버가 굴린다.

### 밧줄

AI 턴에는 밧줄을 붙이지 않는다(`Rope->BeginRope` 를 건너뛴다). 제한 시간은 사람이
고민하느라 판을 세우는 것을 막는 장치인데, AI 는 즉시 결정한다.

대신 **AI 턴에 최소 대기 시간을 둔다.** 카드를 즉시 내면 무슨 일이 일어났는지 읽히지 않는다.
연출이 있는 카드는 연출 길이가 그 역할을 하지만, 연출 없는 카드에는 별도 지연이 필요하다.

## E7. 적 구성과 강화

§16.1 이 정한 두 축 — **적 수 늘리기 + 기본 장비 장착.**

### 배분안

| 조우 | 적 수 | 적 장비 | 성격 | 의도 |
|--:|--:|---|---|---|
| 1 | 2 | — | 무작위 | 기본 루프 학습 |
| 2 | 2 | 각 1 | 무작위 | 장비가 확률을 바꾼다는 것을 본다 |
| 3 | 3 | 각 1 | 공격형 1 | 집중 공격의 압박 |
| 4 | 3 | 각 1 | 공격형 1 · 방해형 1 | 손패 관리 압박 |
| 5 | 4 | 각 1~2 | 혼합 | |
| 6 (보스) | 4 | 각 2 | 공격형 2 | 배신자 1 배치 *(선택)* |

### ⚠️ 체력으로 강화하지 않는다

적 체력을 올리는 것이 가장 쉬운 손잡이지만, §16.2 가 장비 강화를 택한 근거
("장비 카드 시스템을 그대로 쓸 수 있다")를 버리는 선택이다. 체력을 올리면 조우가 길어질 뿐
플레이어가 마주하는 **문제의 종류가 바뀌지 않는다.** 장비는 확률 축을 바꾸므로
플레이어의 대응도 바뀐다.

보스만 예외로 둘 수 있으나, 그때도 체력이 아니라 **장비 2장 + 성격** 으로 먼저 시도한다.

## E8. 보상

§16.5 의 미결정 "레벨당 추가 카드의 획득 방식(선택 보상 / 자동 지급)".

### 결론: 3장 중 1장 선택

자동 지급이면 덱이 커지기만 하고 플레이어가 만든 것이 없다. 선택이 곧 빌드다.

- 조우 승리 시 **3장 제시 → 1장 선택 → 플레이어 덱에 추가**
- **거르기(선택 안 함)를 허용한다.** 덱 상한(32장)이 있는 이상 안 받는 것도 선택이다.
- 2조우마다 **카드 제거 1장**을 대신 제안한다. 덱이 커질수록 시작 덱의 약한 카드가
  원하는 카드를 밀어내므로, 빼는 수단이 없으면 후반에 빌드가 흐려진다.

장비도 같은 자리에서 제시할 수 있다. 장비는 덱에 들어가지 않고 **즉시 장착**되므로
덱 상한을 잡아먹지 않는다 — 장비 보상은 카드 보상보다 항상 매력적이라, 빈도를 낮춰야 한다.

## E9. 구현 단계

각 단계는 **그 단계만으로 검증 가능해야** 한다. AI 를 다 만든 뒤에 켜 보는 방식이면
어디서 틀렸는지 알 수 없다.

| 단계 | 내용 | 검증 |
|---|---|---|
| **E-0** | 봇 PC 스폰 — 좌석만 채우고 아무 행동 안 함 | PvE 로 열면 4인 판이 시작된다. 봇 턴은 밧줄 만료로 넘어간다 |
| **E-1** | 역할 고정 배정 (플레이어=보안관, AI=무법자) | 봇을 전부 죽이면 승리 연출이 뜬다 |
| **E-2** | `UBGAIBrainComponent` — 규칙 4줄 | 봇이 자기 턴에 뱅!을 쓰고 연출이 돈다 |
| **E-3** | 진영별 덱 분리 | 적이 전용 덱에서 뽑는다. `BG_DumpDeck` 이 두 덱을 찍는다 |
| **E-4** | 조우 → 보상 → 다음 조우 | 3조우를 이어서 진행하고 체력·장비가 이어진다 |
| **E-5** | 적 장비 배분 · 성격 | E7 표대로 난이도가 오른다 |

**E-0 과 E-1 이 가장 위험하다.** 봇 PC 가 HUD 를 만들거나(E2 의 함정) 역할 배정이
`CheckWinCondition` 과 어긋나면 그 위의 모든 단계가 흔들린다. 이 둘을 먼저 못 박을 것.

### 검증에 쓸 지표

GDD §11 의 지표를 PvE 에서도 그대로 기록한다. 추가로 둘:

| 지표 | 확인 목적 |
|---|---|
| 런 도달 조우 수 분포 | 난이도 곡선. 3조우에서 끝나면 회복이 부족한 것이다(E4) |
| 보상 카드 선택 분포 | 특정 카드만 고르면 나머지가 보상 후보로 의미가 없다 |

## E10. 미결정으로 남기는 것

이 문서로 답하지 않는다. **플레이 테스트 없이 정하면 근거가 없다.**

- **런 길이** — 조우 6회를 가정했으나 근거는 없다. E-4 이후 실측한다.
- **실패 시 처리** — 런 처음부터 / 마지막 조우 재시도 / 진행도 일부 유지.
  Slay the Spire 는 처음부터지만, 그건 런 하나가 40분이라 성립한다. BAAM 조우가
  얼마나 걸리는지 먼저 재야 한다.
- **런 중간 저장** — 필요 여부가 런 길이에 달려 있다.
- **직업 선택** — 지금 직업 8종이 스탯 차별화가 없어(GDD §7.1 미구현 3종 참고)
  선택이 성립하지 않는다. **PvE 보다 먼저 해결돼야 하는 선행 과제다.**
- **적 전용 직업** — 마왕군 외형을 직업 DT 로 낼지, 별도 축을 둘지.
  아트 기획서의 "마족 사망 시 마족 시체로 변함" 과 함께 정한다.

## E11. 선행 과제

PvE 를 시작하기 전에 PvP 쪽에서 끝나 있어야 하는 것.

| 과제 | 왜 먼저인가 |
|---|---|
| 직업 8종 스탯 차별화 | 직업 선택이 PvE 런의 첫 결정인데 지금은 고를 이유가 없다 |
| 공격·회복·드로우 보정 어트리뷰트 (GDD §7.1 ❌ 3종) | 적 장비로 난이도를 만들 축이 부족하다 |
| `DT_BGCard.json` ↔ uasset 정합 | 덱이 둘로 늘면 어긋났을 때 원인 추적이 두 배로 어려워진다 |

§16 이 "PvP 규칙이 검증된 뒤에 시작한다" 고 못박은 것은 이 셋을 뜻한다.
