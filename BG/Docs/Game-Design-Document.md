# BAAM 게임 기획서

> **문서 상태:** 초기 기획 초안 v0.2  
> **작성 기준일:** 2026-07-30  
> **프로젝트 방향:** 보드게임 《뱅!》의 역할·카드 플레이 구조와 《포 더 킹》의 확률 기반 판정 및 성장 감각을 결합한 PC 턴제 카드 게임  
> **규칙 기준:** 별도로 변경한다고 명시한 항목 외에는 《뱅!》 기본판 규칙을 따른다.

---

## 1. 하이 콘셉트

BAAM은 《뱅!》의 정체 은닉, 역할별 승리 조건, 손패 운용과 공격·회복 중심의 카드 전투를 기반으로 한다. 여기에 모든 즉시 사용 카드의 결과가 확률에 따라 달라지는 판정 구조와, 캐릭터 스탯 및 장비를 통한 확률 보정·성장 요소를 결합한다.

원작의 대면 플레이에서 발생하는 응답 대기와 수트 확인 절차는 PC 환경에 맞게 자동화하거나 제거한다. 플레이어의 핵심 선택은 “누구에게 어떤 카드를 사용할 것인가”, “제한된 카드 사용 기회를 어디에 쓸 것인가”, “확률을 감수할 것인가”에 집중한다.

### 핵심 플레이 감각

1. **역할 추리:** 원작의 역할과 승리 조건을 바탕으로 다른 플레이어의 의도를 추리한다.
2. **제한된 행동 선택:** 한 턴에 사용할 수 있는 카드 수가 제한되므로 우선순위를 정해야 한다.
3. **확률 감수:** 갈색 카드의 결과가 대실패·실패·성공·대성공으로 나뉜다.
4. **빌드 구성:** 캐릭터와 장비가 카드 사용 한도, 성공률, 대성공률 등 전투 성능에 영향을 준다.
5. **빠른 자동 처리:** 피해자의 수동 응답과 수트 확인을 제거해 온라인 턴 흐름을 단축한다.

## 2. 설계 원칙

### 2.1 원작의 정체성은 유지한다

- 역할, 승리 조건, 체력, 손패, 드로우, 버리기 등 기본 골격은 《뱅!》 기본판을 따른다.
- 이 문서에서 변경한 규칙은 원작 규칙보다 우선한다.
- 변경되지 않은 세부 규칙은 우선 원작 규칙을 사용하되, 디지털 환경에서 충돌이 발생하면 별도 항목으로 확정한다.

### 2.2 응답 대기보다 능동적 선택을 우선한다

- 피해자가 카드를 내야 해결되는 응답창을 초기 버전에서 사용하지 않는다.
- `빗나감!`, `인디언!`, `개틀링`처럼 피해자의 응답이 필요한 카드는 **비활성 처리한다**(§13.1 — 삭제하지 않고 경로만 끊는다).
- 향후 추가 카드도 가능한 한 사용 즉시 서버에서 결과가 확정되는 구조로 설계한다.

### 2.3 카드의 불확실성은 확률로 통합한다

- 모든 갈색 카드는 대실패·실패·성공·대성공 중 하나로 판정한다.
- 기존 수트 기반 판정은 모두 확률 기반 판정으로 교체하며 카드 수트는 제거한다.
- 술통, 감옥 등 장비가 요구하는 판정은 시스템이 자동으로 수행한다.

### 2.4 거리보다 대상 선택과 빌드에 집중한다

- 사거리와 좌석 거리 시스템을 **비활성 처리한다**(§13.1). 계산 코드는 남기되 규칙 판정과 UI 표시에서 뺀다.
- 모든 플레이어는 거리와 관계없이 공격 대상으로 선택할 수 있다.
- 사거리만을 변경하는 카드와 장비는 비활성 처리하거나 새로운 효과로 재설계한다.

## 4. 확률 판정 시스템

### 4.1 확정 규칙

- 모든 갈색 카드는 사용할 때 판정을 수행한다.
- 판정 결과는 `대실패`, `실패`, `성공`, `대성공`의 **4단계**다.
- `대실패`는 단순히 효과가 없는 것을 넘어 사용자에게 불리한 결과를 줄 수 있다(반동 피해, 카드 손실 등). 카드별 확정 사항이다.
- `실패`는 효과가 발생하지 않되 추가 불이익은 없는 것을 기본안으로 한다.
- 수트는 판정 데이터와 UI에서 사용하지 않는다.
- 판정은 서버 권한으로 실행하고 모든 플레이어에게 동일한 결과를 표시한다.

### 4.2 권장 계산 구조

아래 구조는 구현을 위한 초기 제안이며 수치는 밸런스 테스트 후 확정한다.

각 갈색 카드는 4단계에 대한 **기본 비율**을 갖는다. 여기에 보정을 더한 뒤 정규화해 누적 구간을 만들고, 난수 한 번으로 구간을 판정한다.

```text
단계별 최종 비율 = 카드 기본 비율(대실패 / 실패 / 성공 / 대성공)
                 + 캐릭터 보정
                 + 장비 보정
                 + 상태 효과 보정

정규화        = 각 비율 / 네 비율의 합        (합이 100 이 되도록)
누적 구간     = 대성공 → 성공 → 실패 → 대실패 순으로 누적
판정          = 0~99 난수 한 번을 누적 구간에 대응
```

- 비율의 합이 100 일 필요는 없다. 시스템이 정규화하므로 기획은 상대 비율로 입력한다.
- 보정으로 특정 단계가 음수가 되면 0 으로 클램프한 뒤 정규화한다.
- 한 카드의 핵심 결과는 이 **한 번의 판정**으로 결정한다(§4.4).
- 최소·최대 확률 제한과 보정 합산 방식(가산 / 승산)은 추후 확정한다.

> **구현 메모:** 현재 `UBaamDiceComponent`가 이미 "4단계 비율 정규화 + 구간 판정" 구조를 쓰고 있다.
> 비율의 출처를 컴포넌트 기본값에서 **카드 데이터**로 옮기고, 보정 합산을 추가하면 이 설계와 일치한다.

### 4.3 카드별 결과 데이터

각 갈색 카드는 최소한 다음 데이터를 가진다.

| 데이터 | 설명 | 현재 상태 |
|---|---|---|
| 기본 대실패 비율 | 보정 전 대실패 상대 비율 | 카드별 확정 필요 |
| 기본 실패 비율 | 보정 전 실패 상대 비율 | 카드별 확정 필요 |
| 기본 성공 비율 | 보정 전 성공 상대 비율 | 카드별 확정 필요 |
| 기본 대성공 비율 | 보정 전 대성공 상대 비율 | 카드별 확정 필요 |
| 대실패 효과 | 사용자에게 불리한 결과(없을 수도 있다) | 카드별 확정 필요 |
| 실패 효과 | 카드 소비 후 발생하는 결과 | 카드별 확정 필요 |
| 성공 효과 | 일반적인 카드 효과 | 카드별 확정 필요 |
| 대성공 효과 | 강화된 카드 효과 | 카드별 확정 필요 |
| 대상 규칙 | 자신, 단일 적, 단일 아군 등 | 카드별 확정 필요 |
| 보정 허용 태그 | 어떤 캐릭터·장비 보정을 받는지 | 구현 시 정의 |

### 4.4 결과 설계 가이드

- 대실패·실패 어느 쪽이든 카드 사용 횟수와 카드는 소비되는 방향을 기본안으로 한다.
- 대성공은 단순 수치 증가뿐 아니라 추가 드로우, 상태 효과, 자원 환급 등 카드 정체성에 맞는 보상을 사용할 수 있다.
- **대실패는 모든 카드에 불이익을 강제하지 않는다.** 카드에 따라 실패와 동일하게 처리해도 된다 — 대실패가 상시 처벌이 되면 공격 카드를 내는 것 자체가 위축된다.
- 대실패 비율은 낮게 유지한다. 통제 불능이라는 인상을 주지 않는 것이 §11 검증 질문 2번의 기준이다.
- 지나친 연속 확률 판정은 턴 흐름을 느리게 하므로 한 카드의 핵심 결과는 가능하면 한 번의 판정으로 결정한다.
- 4단계 확률은 카드 사용 전에 UI에서 확인할 수 있어야 한다.

## 5. 턴과 행동 경제

### 5.1 기본 턴 흐름

1. **턴 시작 자동 처리:** 감옥 등 턴 시작 장비·상태 판정을 자동 실행한다.
2. **드로우:** 《뱅!》 기본판의 카드 드로우 규칙을 적용한다.
3. **카드 사용:** 캐릭터의 턴당 카드 사용 한도만큼 카드를 사용할 수 있다.
4. **정리:** 원작의 손패 제한과 턴 종료 처리를 적용한다.

### 5.2 턴당 카드 사용 한도

- 초기 기본값은 **턴당 2장**이다.
- 이 값은 고정 규칙이 아니라 캐릭터 스탯으로 관리한다.
- 문서상 스탯명은 임시로 `CardUseLimit`을 사용한다.
- 장비, 캐릭터 능력, 상태 효과, 진행도에 따라 증가하거나 감소할 수 있어야 한다.
- 뱅! 전용 사용 제한은 없으므로 `CardUseLimit`이 2라면 한 턴에 뱅!을 최대 2장 사용할 수 있다.

### 5.3 현재 해석과 확인 필요 사항

- “카드 사용”은 플레이어가 손에서 능동적으로 사용하는 카드를 뜻하는 것으로 우선 해석한다.
- 술통·감옥 등 자동 장비 판정은 카드 사용 횟수를 소비하지 않는 것으로 우선 설계한다.
- 장비 카드를 손에서 설치하는 행동이 카드 사용 횟수를 소비하는지는 추후 확정한다.
- 실패한 갈색 카드도 카드 사용 횟수를 소비하는 것을 기본안으로 한다.

## 6. 카드 체계

### 6.1 갈색 카드

- 모두 즉시 판정 후 해결한다.
- 모든 카드는 4단계 결과를 가진다. 단 대실패는 카드에 따라 실패와 동일하게 처리할 수 있다(§4.4).
- 피해자의 수동 응답 없이 서버에서 결과를 확정한다.
- 카드 사용 전에 대상, 성공률, 대성공률, 각 결과의 요약을 표시한다.

### 6.2 비활성 대상

아래 카드는 초기 버전에서 **덱에 등장하지 않는다**. 삭제가 아니라 경로 차단이다(§13.1).

- `빗나감!`
- `인디언!`
- `개틀링`
- 그 밖에 피해자 또는 다른 플레이어의 즉시 응답을 전제로 하는 모든 카드

최종 목록은 기본판 전체 카드 목록을 기준으로 별도 카드 명세에서 확정한다.

### 6.3 파란색 장비 카드

- 설치 후 지속 효과 또는 자동 판정을 제공한다.
- 수트가 필요한 효과는 확률 데이터로 변환한다.
- 거리와 사거리만 변경하는 효과는 사용하지 않는다.
- 술통, 감옥 등 판정형 장비는 플레이어 입력 없이 자동 처리한다.

### 6.4 추가 카드

GAS와 PC 환경의 장점을 활용한 신규 카드는 구현할 수 있다. 다만 초기 재미 검증과 기본 규칙 안정화 이후의 후순위 작업으로 둔다.

신규 카드가 활용할 수 있는 디지털 전용 요소의 예시는 다음과 같다.

- 확률을 일시적으로 올리거나 낮추는 상태 효과
- 다음 판정 결과의 일부를 다시 굴리는 효과
- 카드 사용 한도를 일시적으로 변경하는 효과
- 조건을 만족하면 자동 발동하는 지속 효과
- 전투 기록이나 공개 정보에 따라 강해지는 효과

위 항목은 설계 가능성의 예시이며 실제 카드 채택안은 아니다.

## 7. 캐릭터 스탯

### 7.1 확정 스탯

| 스탯 | 역할 | 초기값 |
|---|---|---|
| 카드 사용 한도 (`CardUseLimit`) | 한 턴에 능동적으로 사용할 수 있는 카드 수 | 2 |

### 7.2 확장 후보 스탯

아래 항목은 장비와 성장 설계를 위한 후보이며 추후 확정한다.

| 후보 스탯 | 역할 |
|---|---|
| 성공률 보정 | 특정 또는 모든 갈색 카드의 성공 확률 변경 |
| 대성공률 보정 | 특정 또는 모든 갈색 카드의 대성공 확률 변경 |
| 공격 보정 | 공격 계열 카드 판정 또는 피해량 변경 |
| 회복 보정 | 회복 계열 카드 판정 또는 회복량 변경 |
| 방어 보정 | 자동 방어 판정 또는 받는 피해 변경 |
| 드로우 보정 | 턴 시작 드로우 또는 추가 드로우 변경 |

스탯 수가 많아지면 카드 확률을 예측하기 어려워질 수 있으므로, 초기 프로토타입에서는 `CardUseLimit`과 소수의 확률 보정만 사용하는 것을 권장한다.

## 8. 장비와 무기 재설계

사거리 시스템 제거로 기존 무기의 핵심 기능이 사라진다. 따라서 무기는 다음 중 하나 이상의 역할을 갖는 빌드 장비로 재설계한다.

- 공격 카드의 성공률 또는 대성공률 보정
- 공격 카드의 성공·대성공 효과 강화
- 특정 카드 유형 사용 시 추가 효과
- 턴당 카드 사용 한도 또는 조건부 추가 사용 기회 제공
- 실패 위험 완화 또는 제한적인 재판정 제공
- 피해, 회복, 드로우 등 다른 캐릭터 스탯 보정

### 장비 설계 원칙

- 단순히 “항상 확률 증가”만 반복하지 않고 서로 다른 플레이 스타일을 만든다.
- 장비 하나가 확률·피해·카드 사용량을 동시에 크게 올리지 않도록 효과 축을 제한한다.
- 장비 효과가 적용된 최종 확률은 카드 사용 전에 UI에서 확인할 수 있어야 한다.
- 거리 전용 장비인 조준경·야생마 계열은 제거 또는 전면 재설계 대상으로 분류한다.

- 자동 판정은 짧은 연출과 로그를 제공하되 별도의 확인 입력을 요구하지 않는다.

## 10. UX 요구사항

- 카드에는 4단계 기본 확률을 항상 표시한다. 표시 공간이 좁으면 최소한 성공+대성공 합산과 대실패 비율을 노출한다.
- 카드 선택 후 장비·캐릭터·상태 효과가 반영된 최종 확률을 표시한다.
- 대실패·실패·성공·대성공을 색상, 아이콘, 텍스트, 짧은 연출로 구분한다.
- 턴 UI에는 `사용한 카드 수 / 현재 카드 사용 한도`를 표시한다.
- 감옥·술통 등 자동 판정은 원인, 확률, 결과를 전투 로그에 기록한다.
- 제거된 사거리 정보와 수트 정보가 카드 UI, 툴팁, 데이터 구조에 남지 않도록 한다.
- 다른 플레이어의 응답을 기다리는 UI는 초기 버전 범위에서 제외한다.

이 기획서는 새 게임 방향의 상위 규칙 문서로 취급한다. 기존 구현 문서 중 아래 설계는 현재 방향과 충돌하므로 후속 정리가 필요하다.

- `Prototype-Workflow.md`의 좌석 기반 거리 설계

- `Card-Implementation-Workflow.md`의 빗나감 응답을 전제로 한 뱅! 처리 단계

기존 코드와 문서를 즉시 삭제하지 않고, 새 프로토타입의 확률 판정과 자동 해결 흐름이 검증된 뒤 관련 항목을 폐기 또는 개정한다.

### 13.1 비활성 처리 원칙 (삭제하지 않고 경로만 끊는다)

이 문서가 "제거" 라고 적은 항목은 **코드·애셋·데이터를 지우는 것이 아니라 호출 경로를 끊는 것**을 뜻한다.

**이유.** 확률 판정과 자동 해결이 아직 플레이 테스트로 검증되지 않았다. 방어 수단 부재(§11 검증 질문 5번)나 집중 공격 문제(4번)가 드러나면 응답 구조나 거리 개념을 부분적으로 되살릴 수 있다. 지운 것을 되살리는 비용이 끊어둔 것을 잇는 비용보다 훨씬 크다.

**수단.** 대상 종류별로 아래 방법을 쓴다.

| 대상 | 비활성 방법 | 되살리는 법 |
|---|---|---|
| 카드 | `DT_BaamCard` 의 `QuantityOfCard = 0` | 값만 되돌린다 |
| Gameplay Ability | `AbilityByCardId` 매핑에서 제외 | 매핑을 다시 넣는다 |
| 어트리뷰트 | 참조하는 코드를 제거하고 선언은 유지 | 참조를 되살린다 |
| 규칙 함수 | 호출처 제거 + `[비활성]` 주석 명시 | 호출을 되살린다 |
| BP 노출 함수 | `meta=(DeprecatedFunction, DeprecationMessage=...)` | 메타만 뗀다 |
| UI 표시 | 뷰모델 채우는 쪽에서 값을 넣지 않음 | 값을 다시 채운다 |

**규칙.**

- 비활성 대상에는 반드시 `[비활성]` 주석과 **사유·복구 방법**을 남긴다. 주석 없는 죽은 코드는 다음 사람이 "버그인가 의도인가" 를 판단할 수 없다.
- 비활성 코드를 **새 코드에서 호출하지 않는다**. 살아 있는 경로와 섞이면 비활성의 의미가 없어진다.
- 비활성 상태를 확인할 수 있어야 한다. 카드는 `Baam_DumpDeck` 이 `QuantityOfCard = 0` 인 종류를 알려준다.
- 비활성 항목은 아래 목록으로 관리한다. 되살리거나 완전 폐기할 때 이 표를 갱신한다.

### 13.2 현재 비활성 대상 목록

| 항목 | 위치 | 상태 |
|---|---|---|
| `빗나감!` / `인디언!` / `개틀링` | `DT_BaamCard` | 확정 — `QuantityOfCard = 0` |
| `GA_Missed` | `Player/Ability/GA_Missed` | 구현되어 있으나 매핑 제외 |
| `GA_AreaBang` | `Player/Ability/GA_AreaBang` | 스텁 상태로 매핑 제외 |
| 응답창(Resolution) 설계 | 미구현 | 착수하지 않는다 |
| 좌석 거리 계산 | `UBaamSeatViewLibrary::GetRingDistance` | 코드 유지, 규칙 판정·UI 표시에서 제외 |
| `WeaponRange` / `DistanceReduction` / `DistanceIncrease` | `UBaamAttributeSet` | 선언 유지, 참조 제거 |

| 무기 5종의 사거리 정의 | `DT_BaamCard` 의 `Magnitude` | 재설계 전까지 `QuantityOfCard = 0` (§8) |
| `FBaamCardRow::CheckChance` | `BaamGameDataTypes.h` | 필드 유지, 참조 제거 — `OutcomeWeights` 로 대체됨 (§4.2) |
| 행운 판정 보정 (`ApplyLuck`) | `UBaamDiceComponent` | 선언·구현 유지, **호출처 없음** — 아래 참조 |

| 능력치 4종 (`Strength` / `Agility` / `Intelligence` / `Luck`) | `UBaamAttributeSet` | 선언·캐릭터 GE 세팅 유지, **어떤 규칙도 읽지 않음** — 아래 참조 |

| `GA_Bang` / `GA_Heal` / `GA_StealOrDiscard` | `Player/Ability/` | 구현 유지, `AbilityByCardId` 매핑 제외 — 범용 실행기가 대체 |

#### 카드 효과 스키마를 하나로 통합한 이유

등급별 수치(`OutcomeMagnitudes`)와 효과 목록(`OutcomeEffects`) 두 필드가 공존하던 동안,
**카드마다 채워야 하는 필드가 달랐고 잘못 채워도 아무 경고가 없었다.**
실제로 뱅의 피해가 들어가지 않는 문제를 겪었는데 — 판정도, GA 발동도, 카드 소비도 모두
정상이고 피해량만 0 이라 원인을 짚기 어려웠다.

이제 모든 갈색 카드가 `OutcomeEffects` 하나만 채우고 `UGA_BaamCardEffects` 로 매핑된다.
`Baam_DumpDeck` 이 빈 효과 데이터를 `[!! 효과 데이터 없음]` 으로 경고한다.

**되살리는 법**: 전용 GA 가 필요한 카드가 생기면(복잡한 연출·다단 판정 등)
해당 카드만 `AbilityByCardId` 에서 전용 GA 로 매핑하고 `OutcomeMagnitudes` 를 채운다.
전용 GA 들은 `EventMagnitude` 폴백 경로를 그대로 갖고 있다.

#### 능력치 4종을 비활성한 이유

§7.1 의 **확정 스탯은 `CardUseLimit` 하나뿐**이고, §7.2 도 *"초기 프로토타입에서는 `CardUseLimit`과
소수의 확률 보정만 사용하는 것을 권장"* 한다. 네 스탯은 그 권고보다 앞서 들어와 있었다.

- **힘 / 지능** — 지능 1 이 `round(1 × 0.5) = 1` 로 피해 1 을 통째로 상쇄해
  "판정은 성공인데 피해 0" 이 되는 문제가 있었다. 카드 수치가 곧 피해여야
  §10 의 효과 표시와 §11 의 밸런스 지표가 성립한다.
- **행운** — 판정 비율에 섞이면 DT 비율이 곧 표시 확률이 아니게 된다(아래 참조).
- **민첩** — 읽던 곳이 비활성 `GA_Missed` 뿐이라 연쇄 비활성.

**되살리는 법**: 확률 보정은 `WeightBonus*` / `WeightMult*` 어트리뷰트로 환산해 캐릭터 GE 로 부여하고,
피해 보정은 `UGA_BaamCardEffects::ApplyDamage` 에서 다시 곱한다.
스탯을 다시 넣을 때는 §7.2 의 경고("스탯 수가 많아지면 카드 확률을 예측하기 어려워진다")를 먼저 볼 것.

#### 행운 보정을 비활성한 이유

판정 비율에 행운을 섞으면 **DT 에 적은 비율이 곧 표시 확률이 아니게 된다.** 그러면
§10 의 "카드 사용 전 최종 확률 표시" 와 §11 의 "설정 확률 vs 실제 체감 비교" 가 둘 다 흐려진다.
초기 밸런스를 잡는 동안은 DT 비율 = 실제 확률을 유지하는 편이 검증에 유리하다.

**되살리는 법**: 두 가지 중 하나를 택한다.
- `UBaamDiceComponent::ApplyModifiers` 안에서 행운 항을 다시 더한다(원래 위치에 주석이 있다), 또는
- 행운을 `WeightBonus*` 어트리뷰트로 환산해 캐릭터 GE 로 부여한다 — 이쪽이 §10 확률 표시와 일관된다.

> ⚠️ **`ApplyModifiers` 호출은 비활성 대상이 아니다.** 이 호출을 빼면 행운뿐 아니라
> 장비의 비율 보정(드워프 장갑·마녀의 부적)까지 함께 죽는다 — GE 가 어트리뷰트를 바꿔도
> 판정이 읽지 않기 때문이다. §8 의 장비 재설계와 §10 의 "장비 효과가 적용된 최종 확률 표시"가
> 이 경로에 의존한다. 실제로 한 번 끊겨서 장비 2종이 무효화된 적이 있다.
